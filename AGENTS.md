## How I want agents to work here
Steps I've asked agents to take differently from the README or their defaults, collected by memgraph from my past sessions (2026-11-24). Full compressed README: `/home/proto/agent-memory/vault/Readmes/apr0t0.github.io.md`. Regenerate with `memgraph readmes --write-agents`; edit outside this block (text inside it is replaced).

1. **Push** — When the user says push, push right away: pull --rebase onto origin/master first (the browser editor commits posts.js remotely), resolve conflicts yourself, push over SSH with a `[ Category ] : Description` message, then confirm the Pages Actions run and check the live site (assets 200, nav link present, console clean, media loads, marker string in the bundle)
   _Instead of:_ Return a push plan, push without rebasing, stop at the push error, or report done without checking the live site · _Why:_ Pushes were rejected because the remote had moved, and an agent once returned a plan when told 'just push' — “it showed some error while pushing so i pulled, resolve it and push again” (2026-07-02)
2. **Preview, then push** — Commit and push only when the user asks or a dictated post is complete. Before that, test locally (local server or Browser pane; open it for the user and tell them to reload each round), stage only the files belonging to the change, and run git diff --check plus node --check on content.js/app.js. On 'show me the preview then push', show the preview and stop; push in a later turn, and say plainly if you already pushed
   _Instead of:_ Commit everything and push in the same turn as the preview, or push every intermediate round · _Why:_ The resume agent pushed in the same turn as the preview, so the user's later go-ahead was moot; the SEM push was gated on a local test — “once done, show me the preview then push” (2026-11-03)
3. **New pages** — In the same change, wire any new page into the homepage nav, the Projects/blog listing (content.js, app.js, posts.js) and a ./<page> terminal command. For standalone folders, add a scripts/check-<page>.mjs step to deploy.yml
   _Instead of:_ Just add a new folder (e.g. sem/) and push · _Why:_ The SEM page shipped unlinked and the user couldn't find it — “its not visible on the main website yet” (2026-08-26)
4. **Verification** — Take real headless-Chrome screenshots at desktop and mobile sizes, over both file:// and http. Test real Enter-submit and touch, check that sprites render as animated characters (not letters or invisible walkers), and check the behaviour for every character or page, not just the test one. Verify 3D in headless Chrome, not the Claude preview pane
   _Instead of:_ jsdom-only tests, or checking only one character · _Why:_ jsdom tests missed the blank file:// terminal and the 'auth setup' Enter-leak bug; pets showed as letters; button perching worked only for boba — “take screenshots, it still just displays the letter symbols instead of actual pets” (2026-07-03)
5. **Big changes** — For big features or redesigns, plan first with explicit choices and wait for a short go-ahead ('let's implement it'); once told 'go ahead with reasonable assumptions', stop asking and build in one pass. A redesign replaces the old site wholesale instead of layering on it and ports every page so each works by click and by ./<page>, square-cornered and text-based. Keep code compact: classic scripts, no build step, no frameworks
   _Instead of:_ Start coding immediately, layer the new UI over the old site, or add frameworks/modules · _Why:_ The user approves plans with short signals and wants a lean repo ('plan a bit meticulously without unncessarily bloating the codexbase') — “We have to get rid of everything in the past for the website and make it tasteful af” (2026-06-30)
6. **Blog posts** — Scaffold the sections as plain editable headings in posts.js first, then fill them one by one as the user dictates, honouring continuity cues ('still the part of the first section'). Use their casual first-person voice, keep every fact and name, invent nothing, and place each photo right after its paragraph. Include all relevant media; use placeholders only when content is truly missing. When the user wants a post 'in just' one statement ('nothing more'), keep it to that
   _Instead of:_ Write a polished post in the agent's own voice with invented details and a few photos · _Why:_ Posts are the user's personal story — “Make sure every section is editable” (2026-10-30)
7. **Media handling** — Pull photos via Drive API v3 from the folder the user names (Eyecandy_media, not the parent EyeCandy admin/CAD folder; stay out of Admin) and re-list it for new uploads rather than assuming none. Convert HEIC with pillow-heif to media/<post>/*.jpg (max 1600 px, quality 82, EXIF stripped to drop GPS). Download linked videos yourself, compress below 100 MB (warn above 50 MB) and add an x.jpg poster when the first frame is black. On 'Reauthentication failed', ask the user to rerun the interactive gcloud auth login
   _Instead of:_ Leave placeholders when Drive is inaccessible, skip HEIC files, or commit full-size originals with metadata · _Why:_ The agent used wrong folder links, missed HEIC files and claimed there were no new uploads — “include images of that from the drive, recently uploaded” (2026-10-31)
8. **Source documents** — Fetch the latest repo state, then use the attached artifact directly (resume PDF, Phased Array Bench HTML from ~/Downloads, a paper figure) and rebuild it natively in the site's light/dark terminal theme with the shared localStorage 'theme' key. Cross-link resume items to existing blogs and projects, and copy the PDF into media/resume/ as an optional download, not the main view
   _Instead of:_ Embed the PDF/HTML as-is, or recreate the content from memory · _Why:_ Pages must look native to the site and stay faithful to the source — “This is my resume, add it in the website theme” (2026-11-03)
9. **Mascots & assets** — Vendor third-party assets into the repo (pets/ via scripts/fetch-pets.mjs, three.js r128 in <page>/vendor/); the only runtime network fetch is an explicit `spawn <name>`. Visitor-facing failures must read cleanly (e.g. 'couldn't reach petdex'), never developer instructions like 'vendor this pet'. Make interactions (perching on buttons, drag-drop, hopping) work for every character
   _Instead of:_ Stream sprites or libraries from a CDN at runtime, surface dev hints in errors, and test one character · _Why:_ The user's ad/tracking blocker killed petdex CDN fetches; a spawn failure told visitors to vendor the character; perching worked only for boba — “first of all don't let the user see to vendor the character xd” (2026-07-03)
10. **Mobile** — Adapt tastefully for phones: 100dvh app-like layout, page-level scrolling (no nested scroll container), a prompt kept above the keyboard, no autofocus (route focus through a gated focusInput()), and a maximize/reading mode. Verify with mobile-size screenshots and leave content untouched
   _Instead of:_ Shrink the desktop layout, autofocus the prompt, scroll inside the terminal box · _Why:_ Nested scrolling blocked the terminal on mobile, and input.focus() pops the keyboard — “make the mobile friendly version for the same as well, get inspiration from similar pages but be tasteful”
11. **3D explainers** — Model scenes on the paper figure the user provides (e.g. GR00T N1, via vla/diagram.js), with generous spacing and a guided camera tour with subtitles that moves along the steps. Scale labels with distance and hide minor labels when zoomed out (ctx.labels.{ref,min,minorBelow}); the user held the push until big labels were fixed
   _Instead of:_ Crowded abstract 3D stacks with large fixed labels · _Why:_ Scene 03 was crowded and unreadable ('make the spacing better ... make the camera move along with the steps'; 'make sure big fonts youu can hide or make them small after that we can push') — “Make sure the visualization have this structure, this one is easier to understand” (2026-11-14)
12. **3D performance** — Optimise for weak machines: lazy next-scene prebuild, DPR cap 1.5, adaptive shadows (PCF 1024), render on demand when paused. Check machine load (e.g. router2l PCB routing jobs) before blaming the page, and don't run long headless captures while the user is browsing
   _Instead of:_ Full-quality continuous rendering; profile only the page · _Why:_ The VLA page was slow on the user's screen, largely because the machine was loaded (load ~14 on 8 cores) plus an agent SwiftShader capture
13. **Robot-learning map** — Update /robot-learning/ only from the robot-learning repo: run PY=<python with omegaconf+pyyaml> scripts/publish_site.sh into a worktree of this repo (not a dirty master), and only after the robot-learning branch has merged, since the map's doc links point at main. Keep research data in graph.research, run node scripts/check-robot-learning.mjs, then push master
   _Instead of:_ Hand-edit robot-learning/ here, serve it from the robot-learning repo's own Pages, or publish before its branch merges · _Why:_ The user wanted the map deployed as an extension of the portfolio like /vla/; the robot-learning Pages workflow was removed (saved memory) — “as an extension of apr0t0.github.io/robot-learning” (2026-11-13)
14. **Agent Remote downloads** — For each new Agent Remote build, bump the version, restage remote/ from the agent-remote repo (npm run apk, build:pages, stage:pages) so the APK and laptop ZIP stable links update together, run node scripts/check-remote.mjs, push, and give the user the direct download link and whether it installs as an update. Keep the page and post in the site's terminal theme and free of relay keys, pairings or logins
   _Instead of:_ Hand over build steps or a local file path without a version bump or a self-test · _Why:_ The user wants a tested, downloadable artifact each time and offered this site for hosting — “test it yourself and provide me with the app that doens't face this issue” (2026-09-14)
15. **Pasted secrets** — Use a token the user pastes only to diagnose the problem (e.g. the blog-editor 403: the fine-grained PAT needs Contents: Read and write). Never write it into files or history, and change nothing beyond what the diagnosis or tests need
   _Instead of:_ Store the token in config or use it for wider changes · _Why:_ The user handed over a GitHub token with an explicit limit — “I am giving you the key to figure it out, don't mess up other than tests” (2026-06-30)
